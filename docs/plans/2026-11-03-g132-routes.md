# G132 ruling 51f — routes, the home-network door, reach away from home

**Status (2026-11-04):** slice 1 built (#586, which includes #572's one-transport work); the door moved to UDP (owner
2026-11-03, ruling 1 below), the TCP fallback kept off by default; slice 2 planned here, not built; hole punching is
design notes only. Read first: ruling 51f in [`TODO.md`](../goals/TODO.md), the research's §12

## Global constraints (ruling 51f, owner 2026-11-03)

- Nothing rented, no cloud mailbox, no Tailscale requirement. Tailscale, when present, is one more route.
- T3 Code's model: an ordered route list, first that answers wins, learned routes saved, earlier routes re-checked on a
  network change, on the app's return and every minute; move back as soon as one works. T3's listener rule: a
  connection closes unless the peer is loopback, private or tailnet.
- D1: no mailbox — "we sync when a machine is on"; an unsent outbox item never expires.
- D3: the door is a sealed-frame endpoint only: never the HTTP API, never a token; off until a memory is shared;
  unauthenticated first packets dropped silently; rate-limited; a small, fuzzed parser.
- Switching networks never re-pairs: identity is the pairing keys.
- The relay is optional, under Advanced, never a default.
- The phone, for now, is a capture device (owner: "right now i want this simple approach"): its captures reach the
  home's queue through the same route list, wait in a durable outbox, land once by `Idempotency-Key`. The full-device
  phone of ruling 51b is deferred. A computer copy (phase 1 B) stays as built.
- Telemetry: which route was used, enums only, never an address.

## Rulings made in the build

1. **UDP, our own small channel, not TCP and not QUIC** (owner 2026-11-03, asked "keep the door on TCP until hole
   punching, or UDP?": *"If we can work on tcp and udp directly probably best to do udp, no?"*; it replaces slice 1's
   first TCP ruling). Two reasons: **silence** — a stranger gets no reply at all, WireGuard-style, where a TCP port shows
   open to any scanner — and **the punch** (2d) needs UDP anyway. Reliability is our own sealed channel
   (`sync_door_channel`, ~600 lines, pure and simulation-tested): a packet number per datagram, WireGuard's replay
   window, ack ranges, RFC 9002's loss rules in small, Reno with a 0.7 decrease, pacing, a receive window, one MTU
   probe. *Why not `aioquic` behind a pre-gate:* the gate would drop every datagram until a signed hello from that
   5-tuple, but behind it a whole QUIC + TLS 1.3 parser (with version negotiation and retry packets it answers on its
   own) becomes reachable by anyone on the LAN who can forge that 5-tuple; the TLS handshake would run beside ours
   (two handshakes, its certificate bound to our keys by hand); it is a new dependency tree (with a C extension) in the
   release bundle; and the phone's Network framework cannot put our raw hello on the same flow before its own QUIC
   handshake. With our channel every datagram after the hello must open under the session key before one byte of it is
   parsed, so the pre-auth surface stays the hello alone; a bug in the reliability code can stall a session, never
   admit a stranger. The phone implements the same in CryptoKit (X25519, P-256, ChaCha20-Poly1305, HKDF) on an
   `NWConnection` UDP flow.
2. **The door's crypto is its own, on the pairing keys, not the relay's epoch frames.** The relay's group (`Endpoint`)
   exists only for devices enrolled at a relay; every paired device already has a P-256 key on the registry
   (`sign_jwk`, or a phone's bound key's thumbprint). P-256 is also the one curve a phone's Secure Enclave signs with.
   So the handshake is a sign-and-DH (SIGMA-like) one: the client's P-256 key, sealed to the door's static X25519 key;
   the door computer's device-key signature over the hello; session keys from both DH results and the transcript.
3. **Pairing over the door**, because a Tailscale-free phone has no other way to reach `/pair`: a one-time 256-bit
   secret (the QR's, never an 8-character code, so a hello captured on the LAN cannot be brute-forced offline) lets one
   request through; the answer is the device's id, never a token.
4. **The door is open while the memory is shared or a device is paired**, so a Mac that only has a phone opens it too.
5. **An outbox entry the home may have seen keeps the 7-day bound**: the home's idempotency key lives 8 days, and a
   resend after that could apply twice. "May have seen" = any answer, or a send whose answer was lost. Never sent =
   never expires. Entries from before the rule keep the old one when they were tried.

6. **The TCP fallback stays in the code and the route list, not bound by default** (`CICADA_SYNC_DOOR_TCP=on` holds
   it). The same handshake and frames on the same port number; a door that holds it says so (`t: ["udp", "tcp"]` in its
   `R` frame and registry `door`), and a device then lists it right after the UDP route of the same kind. Why off: the
   door's slice-1 reach is the LAN and a tailnet, where UDP between the person's own devices passes wherever TCP does
   (a network that isolates clients blocks both), so a bound TCP port would only be a port a scanner sees open —
   against the owner's silence goal — for no route that works. The networks that block UDP are hotel and captive
   ones, reached only through slice 2's mapped port; whether the home maps a TCP port there is decided with 2a. A door
   from before UDP (no `t`) is dialled over TCP, so a dev build of #586 still reaches and is reached.
7. **On a Mac, the UDP door's LAN sockets wait for the app's attribution too.** TN3179: *"Sending a UDP unicast"* to a
   local network address needs the Local Network privilege, *"Listening for and accepting incoming TCP connections"*
   does not — so a UDP door's answers are outgoing datagrams the privilege covers. The door binds its LAN addresses on a
   Mac only when `may_dial_lan` holds (the person's permissions step **and** the agent plist naming the app as its
   responsible code), never under no app's name. (Tailnet traffic crosses a VPN interface, not a local network, but
   its addresses stay behind the same gate, as before.)

## Slice 2 — reach away from home (planned, not built)

Everything below sits behind **"Reach my memory away from home"**, off until the person turns it on, on the home only.

### 2a. Router port mapping

- **PCP (RFC 6887) first, then NAT-PMP (RFC 6886)** — one small pure-Python client (stdlib `socket`, ~300 lines): both
  are a few fixed-layout UDP datagrams to the default gateway on port 5351, both return the external address directly
  (no STUN), both carry a lifetime the home renews at half-life. PCP can also open an IPv6 pinhole on routers that
  support it. *No maintained Python package exists for either; the RFCs are small enough that our own code is the
  smaller risk.*
- **UPnP-IGD as the fallback**: `miniupnpc`'s Python module (BSD-3-Clause, the miniupnp project's own binding, a C
  extension; distro packages ship it for Python 3.14) — but whether PyPI has wheels for every platform the release
  ships was not confirmed, so the alternative is a pure-Python SSDP discover + one SOAP `AddPortMapping` (~250 lines,
  stdlib `urllib`), with the response parsed by a strict allowlist. Recommendation: the pure-Python one, so the release
  bundle carries no new C extension.
- **What is mapped**: the door's UDP port only, to the same external port when free, random high port otherwise
  (the TCP fallback's port too only if slice 2 decides that networks blocking UDP need it — the hotel case, below).
  The door admits a public peer only while a mapping it made is live and the connection arrived on the mapped port;
  every other rule (silent drop, buckets, the handshake) is unchanged. A mapped UDP door shows nothing at all to an
  internet scanner (open and closed look the same: no answer).
- **Networks that block UDP** (many hotel and captive networks): the one place the TCP fallback matters. Decide here,
  with its own measurement, whether the home maps the fallback's TCP port too while the switch is on; until then a
  device on such a network queues (nothing is lost) and lands at the next route that answers.
- **On macOS** a gateway request is a LAN connection: Local Network permission (D4), attributed to the app.
- **Learned route**: the door's `R` frame and the registry's `door` gain `mapped: [{addr, port}]`; the route list gains
  `mapped` after `configured`.
- **Tests**: a fake gateway (a loopback UDP server answering PCP/NAT-PMP and an SSDP/SOAP stub); the real thing is
  measured on the owner's own networks with his OK (it opens a port on his router).

### 2b. IPv6

The home's global IPv6 address (`sync_door.local_addresses()["ipv6"]`, already read) is advertised as `ipv6` only while
the switch is on, and the door admits a global IPv6 peer then. Whether the router admits inbound IPv6 is measured by
the device that tries (the enum says `ipv6` or not). PCP's pinhole opens it where supported.

### 2c. The home's address record in the Mainline DHT (BEP 44, as pkarr does)

- **Why the DHT**: a commons with no operator, no account and no terms to accept; pkarr's records (≤ 1,000 bytes,
  Ed25519-signed, re-published about hourly) are exactly a home's address.
- **Library**: no maintained Python pkarr or BEP 44 client exists (pkarr is Rust; checked 2026-11-03). Options: (i) our
  own BEP 44 `get`/`put` over KRPC in pure Python (bencode, iterative `find_node`/`get_peers` toward
  `sha1(pubkey ‖ salt)`, `get` for a token, `put` with the signature; ~400 lines; Ed25519 from PyNaCl, already pinned);
  (ii) the Rust `pkarr` crate behind a small PyO3 module (a new compiled dependency in the bundle). Recommendation:
  (i), in its own module imported only when the switch is on, behind its own opt-out gate inside the switch (D-new-2).
- **The record**: the home holds a dedicated Ed25519 record key (in `door.json`; its public half goes to devices in the
  registry's `door` and at pairing — never derived from the bank id, so it is unlinkable to it). The value is
  `XChaCha20-Poly1305(k, pad({mapped, ipv6, updated}))` with `k = HKDF(door key ‖ record key, "cicada-dht-v1")`: only a
  device holding both public halves (a device of the group) can read it; the DHT sees random bytes under a random key.
  `seq` is the time; the BEP 44 salt is the epoch day so stale records age out.
- **Re-published** when the home's mapped or IPv6 address changes, and every 45 min (pkarr's guidance is hourly);
  devices read it only after every learned route failed, and cache it 10 min (a cache miss "might take few seconds").
- **On revoke**: a new record key, given to the remaining devices over the door before the next publish.
- **Rail**: DHT traffic is outbound UDP to a commons; some networks treat it as torrenting, so it is one source among
  three (the last learned route, the DHT, an always-on home), never the only one.

### 2d. Hole punching (design notes only)

The punch matters only for a home with no mapping and no usable IPv6. It needs UDP — the door is UDP now (ruling 1),
and its sessions already follow a peer to a new address and port, which is what a punch produces — a reflexive address (BEP 42's `ip`
field in any DHT response, from the same UDP socket the frames use, so the mapping learned is the one punched), and
signalling (each side publishes `{candidates, a punch time}` as an encrypted record, the other polls — seconds, fine for
sync). ProbeLab measured ~70 % success once both sides have candidates; a phone on cellular CGNAT is the common hard
side and fails against a hard home NAT. Build it only if 2a's enums show enough homes with no mapping and no IPv6.

## The Mac-asleep case (the target household: a laptop home and a phone)

What a phone and a Mac pair experiences with slice 1, measured on loopback (`test_sync_door_phone.py`):

- **Both awake, same Wi-Fi**: a capture lands in the home's episode queue in ~10 ms (loopback; a real Wi-Fi hop adds its
  round trip); a computer copy is told of a commit by the door's watch and fast-forwards in a few hundred ms.
- **The Mac asleep** (lid shut — the normal state): the phone's captures wait in its own outbox; reads on a computer
  copy come from its own copy; nothing expires however long the Mac stays shut (a month in the test).
- **The overlap**: the first time both are awake and a route answers, every waiting capture lands once, in order (three
  captures in ~20 ms after the home answered, one of them re-sent after a lost answer and kept once).
- **Away from home**: nothing reaches the Mac until slice 2 or the person's tailnet; captures land on the next overlap
  at home.
- **No push**: without a server holding Cicada's push key the Mac cannot wake the phone; it learns of new inbox
  questions when opened.

## What the phone app needs from this transport (a later build)

`api/tests/_phone_like.py` is the reference; the app implements the same in Swift (or its React Native module):

1. **Its key**: a Secure-Enclave P-256 key; ES256 signatures as raw `r‖s`.
2. **Pairing**: scan the QR v2 carrying `/devices/pairing`'s `door` (`home`, `sign`, `key`, `port`, `lan`, `tailnet`,
   `pair`) and the code; `sync_door.pair` over the LAN door; keep the device id. No token is needed or given.
3. **The door client**, over UDP (`NWConnection` with `.udp`): the hello datagram (`client_hello`, the same bytes
   resent if no reply), `client_finish`, then `sync_door_channel`'s packets — packet numbers, the replay window, acks,
   retransmission, pacing — carrying `u32 length ‖ kind ‖ data` frames; one request per session at a time, `R` frames
   saved as learned routes; a ping every 25 s while a session is held and at once on `NWPathMonitor`'s change.
4. **The route list**: Bonjour browse for `_cicada._udp` with the memory's instance name (Network framework,
   `NWBrowser`, with the Local Network usage text), then learned routes; `NWPathMonitor` → re-check every route;
   `sync_routes.Book`'s rules (first that answers, 60 s down, move back).
5. **The outbox**: one durable entry per capture with its `Idempotency-Key`, sent oldest first, kept until an answer;
   never expires unless the home may have seen it 7 days ago; foreground and background-refresh flushes.
6. **Captures only**: `/capture/note`, `/capture/file`, `/sources/save` — the capture-only scope the door enforces.
7. **Export compliance**: the app now carries end-to-end encryption; `ITSAppUsesNonExemptEncryption` must be revisited.
