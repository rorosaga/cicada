# G132 — one memory on every device: a sync engine

**Status:** design plan, 2026-10-29. Phase 1's task plan (exact files, tests, commands) is written after the owner
answers §7; nothing here is built yet.

**Owner, 2026-10-29:** "Changing the 'main machine' should be easy and all machines should have the same copy of
memory. I've read a lot about Linear having a good sync engine, maybe we should aim towards that? … for avg user that
wants to just download the cicada app, also downloading tailscale might be friction … even through my phone I should be
able to have the conversation and go through my inbox … My phone should be another device in the network, not one that
independently syncs to [each computer] separately."

## 1. What is true today

- **One primary per bank (G181).** A server is its bank's only git writer and runs its Sleep; another machine is a
  client (`CICADA_API_BASE` + a device token) with **no bank of its own**. Every read a client makes is a network round
  trip, and when the primary sleeps (a laptop lid) every client loses its memory.
- **In practice the owner has two unrelated banks.** A computer that was never pointed at the other runs its own
  backend and Sleep: two inboxes, two queues, two graphs. Nothing converges them, by design (G132: git pull/merge and
  file syncers break the id rule, the read-modify-write state files and Sleep's single mind).
- **Reach needs an overlay.** The backend binds 127.0.0.1; another device reaches it through Tailscale (`tailscale
  serve`, one click since 2026-10-29) or an SSH tunnel. A person who only downloads the Cicada app must also install,
  sign in to and keep running a VPN — and their phone must too.
- **The phone is capture-only (ruling 38 §2, 2026-10-23).** It posts notes and shares; it cannot read the graph, answer
  the inbox or hold a conversation. **The owner reverses this today** (§6; recorded as ruling 51 in phase 0).
- **Pieces that already exist and carry over:** per-device tokens, revocable, a phone's bound to a Secure-Enclave key
  (`device_tokens`, `device_proof`); pairing by one-time code/QR (`POST /pair`); `POST /tools/call`, which runs every
  MCP tool body on the server; the hook spool and the app's outbox with an `Idempotency-Key` per item and the bank id
  it was meant for (`idempotency`, G202); the bank id in `banks.yaml`; the cheap version vector `/sync/version` and
  `/sync/events` (G58); write admission (`write_admission`) and `episode_lock`.

## 2. What Linear actually does, and what carries over

Linear's sync engine (Tuomas Artman's talks; the community reverse-engineering of its client) in five moves:

1. **Every client holds a local copy** (IndexedDB) and reads from it — the UI never waits on the network.
2. **One server orders everything.** Each accepted change gets a monotonically increasing `syncId`; the server's log
   is the single truth. There is no peer-to-peer merge and no CRDT for most data.
3. **Clients write transactions, not state.** A mutation is applied optimistically to the local copy, queued
   (persisted, survives a reload), and sent to the server. The server validates and applies it, or rejects it and the
   client rolls back.
4. **Deltas fan out.** The server pushes `SyncAction`s (the new syncIds and what changed) over a websocket; a client
   that was away asks for "everything since my `lastSyncId`". A client too far behind re-bootstraps.
5. **Bootstrap can be partial.** Large or rarely used models load lazily; a client never needs everything up front.

**Why it fits Cicada better than a CRDT or git merge.** Cicada's hard invariants — the id rule, write admission,
Sleep's single mind, "contradictory facts can merge cleanly" (G132) — all assume *one orderer*. Linear keeps the
orderer and moves everything else to the edges. So does this plan:

| Linear | Cicada |
|---|---|
| the server that assigns syncIds | the **home** device: the one replica that applies writes and runs Sleep |
| syncId | the home's git commit sequence (a linear, fast-forward-only history, numbered) |
| local IndexedDB copy | a **replica**: the bank's git checkout + its derived index, on every computer |
| transaction queue | the outbox that already exists, generalized: every write tool call, idempotency-keyed |
| SyncAction delta | "commits N..M" — a git pack or, for the phone, a JSON delta of the pages that changed |
| partial bootstrap | the phone's replica: the inbox, the entity index and recently used pages, lazily the rest |

What does **not** carry over: Linear's server is always-on cloud. Cicada's home is the person's own machine, so (a)
the home can be offline — transactions must wait somewhere — and (b) the home must be movable. §4 and §5 answer both.

## 3. The model

- **Every computer holds a full replica** of the bank. Recall, the graph, `cicada_ask`'s retrieval, the app's pages and
  the MCP read tools all answer from the local replica: instant, and working with the home asleep or the network gone.
- **Exactly one replica is the home.** It alone applies transactions, mints ids (the id rule holds unchanged: ids are
  minted where they always were, at apply time, under the same lock), commits, and runs Sleep. Every commit it makes is
  a sync step; its history only ever grows (no rebase, no force).
- **Every write is a transaction.** Capture, save, resolve an inbox item, write/retract a claim, edit a page, add a
  backlog item: on a non-home device each becomes `{id (idempotency key), device, bank_id, base_seq, tool, args}`,
  persisted in the device's outbox and sent to the home. The home applies it through **the same tool body** it runs
  today (`/tools/call`), so every rail (scrub, staging, demo guard, authorship, write admission) holds by construction.
  A transaction that no longer applies (the inbox item was already answered elsewhere) is rejected with a reason, and
  the device drops its optimistic state.
- **Replicas fast-forward.** A replica at seq N asks for N..head. Computers fetch git objects (a pack) and fast-forward;
  a replica never commits on its own, so a fast-forward always succeeds. The derived index updates incrementally from
  the changed paths (it is already rebuilt from files, never synced).
- **Optimistic local state (phase 4).** Until the home confirms, the device shows its own pending transactions on top
  of the replica (an answered inbox item disappears at once, marked "waiting for <home>"), the way Linear does.

## 3a. The consolidation queue is the same on every device

The queue is not per-machine state; it is the bank's, so every device shows the same one:

- **What Sleep will read** is the replica's `processed: false` episodes — replicated like every page, so a phone, a
  computer and the home all count the same list, at the same sequence number. A Sleep that starts or finishes on the
  home is a commit; every device sees the queue empty or fill at its next delta.
- **What is on its way** is shown beside it, never mixed in: this device's own outbox ("3 conversations captured here,
  waiting to reach <home>"), and the relay mailbox's count per sending device (a count the relay already sees as
  metadata; never content). So a capture made on the train is visible as queued from the moment it is captured, on
  that device, and as queued on every device from the moment it reaches the relay.
- **Sleep's own state** — running, its stage, the last run, the schedule — is published by the home as a small status
  frame, so "Sleep now" pressed on any device is a transaction to the home and its progress is seen everywhere.
- **The inbox the same way:** the items are pages in the replica; an answer given on one device disappears on every
  other at the next delta, and optimistically at once on the device that answered.

## 4. Moving the home — easy by construction

Because every replica is a prefix of one linear history, "move the home to X" is:

1. X catches up to the current home's head (it usually already is).
2. The current home stops admitting transactions (write admission already exists), finishes or parks a running Sleep,
   and writes a **hand-off record**: `{bank_id, seq, from, to, at}` signed with its device key, as the last commit.
3. X fast-forwards to that commit, verifies it, and starts admitting. Every device learns the new home from the
   commit itself; queued transactions re-target automatically (they carry `bank_id`, not an address).

One command and one button: `cicada home move <device>` / Settings → Devices → *Make this the home*.
**If the home is gone for good** (a lost laptop): any replica may *take over* after the person confirms. What it loses
is exactly the commits it had not received — the replication lag, shown before they confirm ("this device is 0
changes behind the last home it saw, 2 minutes ago"). The old home, if it ever comes back, sees a newer hand-off and
becomes a replica; any of its later commits are offered back as transactions, never merged.

## 5. Reaching each other without a VPN — the relay

Every device dials **out** to a relay over a websocket; the relay forwards frames between the person's own devices.
Nothing listens on a public port, nothing needs a VPN app, and NATs, hotel Wi-Fi and the metro do not matter.

- **End-to-end encrypted.** Pairing (the QR, which already exists) carries the bank's device-group key; every frame is
  encrypted to the person's devices. The relay sees sizes, timing and device ids — never a page, a transcript or a
  token. It cannot read or forge memory.
- **Store-and-forward mailbox.** When the home is asleep, a device's transactions wait at the relay (encrypted, bounded,
  expiring), and are delivered when the home reconnects. Deltas wait the same way for a phone that was off.
- **Direct when possible.** On the same LAN or tailnet, devices talk directly (the relay is the fallback, the way
  Tailscale's own DERP is). Tailscale stays supported; it stops being required.
- **Self-hostable.** The relay is a small stateless-ish service with one mailbox per bank. Cicada can run a hosted one
  for people who just download the app; anyone can run their own (one container) and point the app at it.
- **Candidate stacks** (to be measured in phase 3, not decided here): a Cloudflare Durable Object per bank (the
  mailbox and fan-out are what DOs are for); a small Python/Go websocket relay on any host; or iroh (QUIC, hole
  punching with relay fallback, has Python bindings) for direct device-to-device with a relay only as fallback.

## 6. The phone as a full device

The phone becomes a device on the same footing as a computer, through the same relay, never a separate sync to each
computer:

- **A partial replica.** The inbox, the entity index (names, types, one-line summaries), the pages it opened recently
  and the current-projects view, as JSON deltas keyed by the same sequence; the rest lazily, on open.
- **The inbox on the phone.** Answering, skipping and opening a question's sources are transactions, optimistic on the
  phone, applied at the home.
- **Conversations on the phone.** Two paths, not exclusive: (a) the Claude and ChatGPT apps with Cicada's connector
  (G135), which today needs a public listener the person funnels — through the relay instead, it needs none; (b) a
  chat inside the Cicada app, on the person's own model plan, whose tool calls read the phone's replica and write
  transactions. The conversation itself is captured as an episode like any other.
- **Token and key.** The phone's token stays bound to its Secure-Enclave key (already built), now with full scope;
  revocation from any device removes it from the device group and rotates the group key.

## 7. Decisions for the owner

1. **A Cicada-hosted relay** (end-to-end encrypted, self-hostable alternative) — yes/no. It is the only way "download
   the app and it works" holds without a VPN; it is also the first time Cicada runs a service. *Recommended: yes.*
2. ~~Where Sleep runs~~ — **decided (owner 2026-10-29): the home runs every consolidation.** "the main device runs
   consolidations. Consolidation queues for example should be in sync." Sleep is unchanged and runs only on the home;
   moving the home moves Sleep with it (§4 parks a running Sleep before the hand-off).
3. **The phone's chat:** the Claude/ChatGPT apps over the relay first (recommended — no model integration in the phone
   app), or a native chat in the Cicada app first.
4. **The two banks the owner has now:** which one becomes the home, and whether the other's waiting conversations and
   inbox are replayed into it as transactions (recommended: the larger becomes home; the other's *unprocessed*
   episodes are replayed as captures, its graph and inbox are dropped, since Sleep regenerates them).

## 9. Global constraints (every phase)

- One orderer per bank; histories only fast-forward; nothing is ever merged by git or a file syncer (G132).
- The id rule, write admission, scrub/staging, the demo guard and authorship are applied at the home, by the tool
  bodies that apply them today — a transaction is a tool call, never a file diff.
- Capture never blocks on the network: an unreachable home queues, it does not fail (the spool's existing promise).
- No plaintext memory leaves the person's devices; the relay is untrusted by design.
- Unset/off, nothing changes: a single-machine install has no relay, no replica mode, no new process.
- The privacy rule: no hostnames, names or bank content in this plan, the row, commits or PRs.
