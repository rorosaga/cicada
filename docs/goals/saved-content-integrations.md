## Aggregator verdict (Composio, Zernio, the field)

VERDICT ON COMPOSIO / ZERNIO / AGGREGATORS FOR CICADA

They do not earn a place today, for three stacked reasons:

1) They cannot deliver the actual read surfaces. Composio's toolkits wrap exactly the generic business APIs: IG (29 actions, Graph API, business-only) has no saved-posts action; YouTube (47) has no history/Watch Later; LinkedIn (22) has no saved items. Zernio is a hosted *publishing* API (post/schedule/DMs/analytics) — zero personal saved-content reads. These gaps are upstream (the platform APIs don't expose the data), so NO official-API aggregator can ever close them. The one platform an aggregator does cover — Pinterest — requires bring-your-own OAuth credentials on Composio anyway, at which point a direct v5 integration is strictly less moving parts.

2) They violate the local-first posture structurally, not incidentally. Every hosted aggregator (Composio, Pipedream Connect, Arcade, Klavis Cloud, Zernio) stores OAuth tokens server-side and proxies tool-call request/response content through their cloud; per a competitor's report (unconfirmed by Composio directly), even BYO-OAuth Composio setups register Composio's callback URL so tokens land in their cloud. Enterprise self-hosting exists but is priced for companies, not a personal thesis app. Cicada's whole pitch is provenance-obsessed, on-device memory — routing saved-post content through a third party's SOC 2 cloud is a category error, not a tradeoff.

3) The field is unstable: mcp.run sunset within ~a year; Klavis and ACI.dev both show pivot signals away from their integration platforms. Not dependencies to build a thesis on.

When they WOULD earn a place: if Cicada ever needs many *write/action* integrations (post to X, create a calendar event, send a Slack message) across dozens of services, managed-auth aggregators genuinely remove OAuth plumbing — and at that point the posture-compatible choice is Nango free self-host (ELv2, docker-compose, token layer on the user's machine, BYO platform OAuth apps) or Klavis's Apache-2.0 per-platform MCP server images run locally — never a hosted proxy. For the current goal (reading personal saved indexes), the honest architecture is: export importers (4 platforms), two direct APIs (Pinterest, Reddit), and explicitly-opt-in local browser reads for the two surfaces with no other route (YT Watch Later; LinkedIn post bodies — recommend skipping the latter entirely).

## Graph derivation for saved items

HOW SAVED ITEMS DERIVE RELATIONSHIPS (using the machinery that already exists — verified in-repo)

The pipeline already does the right thing for intentional saves; new importers need only feed it well. The existing two-hop path: (1) every saved item writes a `processed: false` episode whose body carries title/site/channel/folder/description/user-note, so normal Sleep Stage 1–2 extraction/resolution runs over it source-agnostically (`sleep_cycle._get_unprocessed_episodes`) and produces concept/tool/person entities — a saved recipe post's title/description yields a `cooking` concept exactly like conversation text would; (2) Stage 5.55 `inject_media_edges` (media_ingestor.py:1258-1317) joins each media entity's `source_episodes` against entities resolved that cycle and writes `media —about→ entity` edges into graph_edges.yaml (sole canonical edge store), deliberately bypassing the promotion gate — a save is an intentional act. (3) Stage 5.57 `link_enrichment` adds `describes` claims (on-page description → claim, no-LLM reuse path when substantive) and `recommends` claims (person who shared → media), and Stage 5.7 `regenerate_edges_from_claims` projects claims into edges — VERIFIED this session: only `object_kind == 'node'` claims project, so `recommends` (person→media) becomes an edge and `describes` (string object) correctly does not.

Three concrete additions for the new sources:

(a) ENRICH AT INGEST OR STAGE 1 STARVES. Stage 1 can only extract from episode-body text. YT playlist CSVs (no titles) already get oEmbed enrichment at ingest; Reddit export rows (id+permalink only) must be hydrated via the Reddit API (`/api/info`) at ingest; LinkedIn saved items (URL+date only) cannot be enriched (login wall, §8.2) — accept thin nodes whose only edges come from folder tags, and say so in the UI. TikTok entries carry Date+Link; oEmbed (`tiktok.com/oembed`) plausibly fills titles — not verified this session.

(b) WATCH HISTORY MUST GO THROUGH THE PROMOTION GATE, NOT `write_media_entity`. The G47 bypass is justified for saves (intentional); watch history is ambient exhaust. Minting a media entity per watched video would flood the graph (and slam straight into G65's collision/junk debt). Route history entries as episodes only, and let the normal promotion model do its job: a channel or topic watched across 2+ sessions meets the existing threshold and gets promoted with backfilled context; one-off videos stay in the sqlite-vec index. This is exactly what the promotion model was designed for.

(c) FOLDERS/COLLECTIONS ARE THE STRONGEST UNUSED SIGNAL. An Instagram collection name or Pinterest board name ("recipes", "type-inspo") is a user-authored topic label; today it becomes only a sanitized tag slug. Promote a folder with ≥2 member saves to a `concept` entity (the recurrence threshold is already met by definition — each save is a separate episode mentioning it) and emit `media —about→ concept` edges through the same Stage 5.55 join. For topical claims beyond `about`, the predicate registry defaults unseen predicates to multi-valued/coexist (VERIFIED: predicates.py:171-186), so e.g. `covers-topic` needs zero registry change — but resist vocabulary sprawl; `about` covers most cases. Prerequisite before scaling any of this: fix G65(a/b) — the title-slug entity-id collisions (148 consent pages on one entity) and consent-wall junk detection — or bulk API polls will multiply the debt.

## The consume layer (watching/reading saved items later)

CONSUME LAYER (options only): For actually watching/reading a saved item later and turning it into memory, the candidates are: (1) YouTube — transcript-first: `youtube-transcript-api` or a locally-run Klavis YouTube MCP server (Apache-2.0, transcripts+metadata via a Data API key; explicitly cannot read history), falling back to `yt-dlp` audio + local Whisper/whisper.cpp for caption-less videos; (2) articles/generic URLs — readability extraction (trafilatura / readability-lxml) feeding the existing Stage 5.57 fetch+LLM-summarize path on the G49 engine ladder (subscription CLI → local → BYOK), which is already offline-safe (fetch/LLM failure writes no claim); (3) login-walled posts (Instagram, LinkedIn) — an explicit opt-in "read this one now" via Claude-in-Chrome / the browser-harness skill driving the user's own logged-in Chrome (the Claude-in-Chrome model: inherits sessions, per-site permissions, never enters credentials), never a background job; (4) images/screenshots — a local VLM via Ollama (e.g. a qwen-VL-class model) or the subscription CLI's vision, producing the summary a `media` entity's schema already expects; (5) packaging — either an agent skill in the ZeroPointRepo/youtube-skills style or a `cicada_consume` MCP tool, in both cases writing the result as a `describes` claim on the media page (Stage 5.57's no-LLM reuse path then picks it up), bumping `last_referenced`, and recording a ledger event in `~/.cicada/telemetry/` so consumption cost is visible in the G51 dashboard.

## Design memory sketch

DESIGN-MEMORY SKETCH — screenshots of design-saved websites as memory

CAPTURE ROUTE. No screenshot capture exists anywhere in api/ or app/ today (verified by grep this session). Given Cicada's local tooling, the honest ladder is: (1) default, keyless — a Sleep tail step (pattern-match `warm_logos`) that renders pending design-tagged media URLs with headless system Chrome (`"Google Chrome" --headless --screenshot=... --window-size=1440,2400 <url>`), bounded by a small semaphore, offline-safe (failure = no screenshot, retry next cycle); (2) for login-walled inspiration (Dribbble likes, private Figma) — an explicit opt-in capture through the user's own logged-in browser (Claude-in-Chrome / browser-harness CDP), on-demand only; (3) `screencapture -v` is for demo recordings, not this — it captures the screen, needs TCC, and can't render a URL (the user's env-quirks memory note is about exactly that friction). Later, the G37 share-sheet becomes the capture-at-save-time route.

STORAGE — OUTSIDE BANKS, exactly like logos. A screenshot of someone else's website is a derived artifact of the outside world, not versioned memory — the same argument logo_service already encodes ("never inside a bank"). So: `~/.cicada/screens/<bank>/<url_hash>.png` + `meta.json` index, served by `GET /entities/{id}/screenshot` (ETag, long max-age), a `has_screenshot` flag on graph nodes set from the index only (no network in /graph), ~30-day TTL so redesigned sites refresh. The moment the user annotates or crops one, THAT becomes memory: write the annotation as body text / a claim on the media entity in the bank; the pixels stay derived.

DESIGN IDENTITY — three layers on existing schema, zero schema change. (i) Per-item claims: a Sleep-time VLM pass (G49 engine ladder; keyless degrade = skip silently) over each screenshot emits claims on the media entity — `palette` (hex list), `typography` ("grotesque sans, tight leading"), `layout-style` ("dense editorial grid") — all unseen predicates, which the registry defaults to multi-valued/coexist (verified, predicates.py:171-186), so no seed change. (ii) Style concepts + edges: `exemplifies-style` claims with node objects pointing at style `concept` entities ("brutalist web", "warm neutrals") — these project into real graph edges at Stage 5.7 because they have `object_kind: node` (verified: only node-object claims project), clustering the inspiration corpus visually in the d3 graph; the save-folder name ("design", a Pinterest board) rides the folder→tag path and the folder-promotion idea from graph_derivation. (iii) The identity itself: a `skill`-type entity ("Design taste: dense editorial layouts, muted warm palettes, grotesque type") distilled by Stage 4 pattern detection across design-tagged saves — Stage 4's literal job description (recurring patterns → procedural skill entities), just pointed at saves instead of conversations.

HERO/PREVIEW MACHINERY. `MediaPreview`/`HeroPreview` already dispatch on media_type with an `image` kind that has no server-side writer today — the screenshot becomes the hero image for `url`-kind design media (preferred over the OG card when present), and the entity page's rendered tab gets the palette swatches under the G24 SummaryBox. Prereq: G65(a) slug-collision fix, since design saves are exactly the title-poor, junk-prone bulk imports that triggered it.
